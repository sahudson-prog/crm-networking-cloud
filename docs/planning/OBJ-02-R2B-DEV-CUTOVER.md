# OBJ-02 R2-B: preparación y cutover DEV

Según el operador, las migrations `202610270002` y `202610280001`, sus preflights y ambos verifiers dieron PASS en DEV; el smoke funcional/UX del candidato local en `http://localhost:3000` también dio PASS informado. El gate volvió a `paused`, sin usuarios admitidos, con RPCs sensibles bloqueadas, Data API y Auth signup OFF, y runtime detenido. No hay evidencia individual de todos los escenarios críticos con el SHA que se publica. Los pasos SQL ejecutados se conservan como registro y no se repiten. DEV no tiene Vercel ni URL hospedada; el siguiente gate es una validación focal del SHA publicado en el runtime local antes de `open`. PROD tiene un gate separado.

## Contrato y recuperación

`202610270002_networking_cycle_operations_v1.sql` es **PROD CONTRACT CHANGE**. Cambia los permisos de escritura, obliga a presentar un contexto de ciclo vigente y congela observaciones al cerrar. El runtime anterior deja de ser seguro al instalarla: sus escritores de Prioridades, asociaciones, estado/foco y merge no presentan ese contexto. Aunque la instalación termine con el gate `paused`, no reabrir el runtime anterior. El primer cierre hace además incompatible cualquier intento de reconstruir el estado con el runtime anterior.

La migration es transaccional y comienza con el gate `paused`. Una falla de instalación revierte toda la transaction; conservar la pausa, investigar y reintentar solo después de resolver la causa. Si falla el verifier o el smoke después del commit, conservar el schema y los datos, volver a `paused` y preparar un forward-fix. No reescribir la migration instalada ni ejecutar un rollback SQL ad hoc. Una restauración completa solo procede con un punto consistente, ensayo y aprobación operativa, por separado.

El preflight comprueba compatibilidad y algunas invariantes agregadas; no captura definiciones de schema, funciones, permisos o distribución de los datos afectados. La captura read-only `cloud/supabase/operations/dev/202610270002_capture_networking_cycle_operations_v1.sql` registra esos contratos y conteos agregados inmediatamente antes de la migration. No incluye filas personales y **no es un backup recuperable**. Para DEV, determinar antes del corte si contiene datos irremplazables y si existe una restauración probada del proyecto. Si hay datos irremplazables sin recuperación probada, capturar un backup lógico verificable y ensayar su restauración aislada antes de instalar. Si los datos son reproducibles y la recuperación transaccional más forward-fix es suficiente, no exigir por defecto un backup completo de DEV. PROD mantiene el gate de backup recuperable de `docs/PROD_CONTRACTS.md`.

## Orden ejecutable

1. Registrar proyecto DEV, URL y referencia de proyecto desde la configuración operacional; verificar explícitamente que el runtime local y la conexión SQL apuntan a DEV. Registrar el SHA del candidato ejecutado en `http://localhost:3000`. No usar credenciales ni conexiones PROD.
2. Ejecutar `cloud/supabase/preflight/202610270002_preflight_networking_cycle_operations_v1.sql` en lectura. Exigir `installation_state = clean_install`, incluido el hash del contrato de acceso efectivo. Guardar el resultado y las métricas; si no coincide, **STOP**. Resolver la decisión de recuperación de DEV anterior. El preflight no sustituye la captura del paso 3.
3. Programar una ventana de mantenimiento. Deshabilitar la Data API del proyecto DEV desde Supabase, detener los jobs y cualquier conexión Postgres directa que escriba, y deshabilitar registros Auth durante la ventana. No basta con esconder botones ni cerrar navegadores. Confirmar que no quedan otros canales de escritura de la app. Ejecutar `cloud/supabase/operations/dev/202610270002_check_write_pause.sql` como operador SQL y exigir cero transacciones de clientes activas; clasificar explícitamente cualquier conexión directa observada. Con la pausa comprobada y antes de la migration, ejecutar `cloud/supabase/operations/dev/202610270002_capture_networking_cycle_operations_v1.sql` y guardar su resultado íntegro en un lugar privado junto con el preflight. **PASS:** una fila, `capture_state = complete`, `before_r2b = true`, `missing_relations = []`, `missing_functions = []`, `payload_bytes > 0` y `payload_md5` presente. `complete` también exige cero ciclos cerrados, cero Prioridades sin ciclo y cero discrepancias de ownership de Prioridades o asociaciones al momento de capturar. Si falla el SQL, falta el resultado íntegro o no se cumple cualquiera de esos criterios, **STOP** y mantener la pausa; la captura no autoriza continuar sin la decisión de recuperación del paso 2.
4. Con escrituras detenidas, ejecutar `cloud/supabase/migrations/202610270002_networking_cycle_operations_v1.sql`. Exigir commit completo. Ejecutar `cloud/supabase/verifiers/202610270002_verify_networking_cycle_operations_v1.sql`; exigir `verdict = pass`. El gate debe permanecer `paused`; no habilitar uso normal.
5. Preparar un único usuario Auth de prueba autorizado en DEV y configurar el runtime candidato **local** con el proyecto DEV. Rehabilitar la Data API; mantener detenidos jobs/escritores directos y registros Auth. Ejecutar `cloud/supabase/operations/dev/202610270002_set_test_only.sql` tras sustituir el UUID cero por el ID real de ese usuario. Confirmar que su acceso es permitido, el de otro usuario es denegado y los RPCs de servidor `submit_contact_request_v1` y `finalize_google_connected_account_verified` siguen revocados a `service_role`.
6. Hacer smoke autenticado con el candidato local: onboarding completado/en progreso/replay, entrada sin creación de ciclo, configuración legacy, inicio retroactivo y zona, cierre en instante exacto, conservación de datos cerrados sin listado visible, reinicios independientes, Prioridades/asociaciones, Coach, sync/import y merge. Verificar que una sesión antigua falla en las escrituras ligadas al ciclo, que una edición global de identidad funciona, y que otro usuario no puede leer observaciones cerradas. Registrar resultados y errores sin PII. Si falla, deshabilitar de nuevo Data API, drenar, ejecutar `cloud/supabase/operations/dev/202610270002_set_paused.sql`, conservar R2-B y corregir localmente; no volver a R2-A.
7. Tras publicar la branch, iniciar el SHA exacto publicado en el runtime local `http://localhost:3000` con variables exclusivamente DEV. Para la validación focal, repetir la preparación controlada de `test_only`: único tester identificado, Data API ON solo durante la prueba, Auth signup y escritores auxiliares OFF. Confirmar SHA y entorno antes del smoke autenticado; documentar los casos críticos sin evidencia individual. Al terminar, detener runtime, deshabilitar Data API, drenar y restaurar `paused` con cero usuarios admitidos. El smoke general informado del candidato previo no certifica automáticamente el SHA publicado ni cada subcaso.
8. Si la evidencia focal pasa, preparar por separado la apertura de DEV con el mismo SHA compatible en el runtime local. Comprobar proyecto y variables DEV, escritores auxiliares y ausencia de sesiones antiguas; habilitar Data API y ejecutar `cloud/supabase/operations/dev/202610270002_set_open.sql` solo con autorización operacional. La transición abre acceso efectivo y reotorga atómicamente los dos RPCs de servidor. Rehabilitar jobs/escritores directos **solo después** de verificar que usan el contrato nuevo, y registros Auth según la política DEV. Verificar lectura y escritura autenticadas de uso normal, y registrar hora/operador/evidencia.

Ante un fallo posterior a `open`, detener primero la Data API y los escritores directos, esperar drenaje y ejecutar `202610270002_set_paused.sql`; después aplicar forward-fix. Cambiar el gate sin drenar no cancela transacciones que ya pasaron la comprobación de acceso. La Data API deshabilitada impide llamadas REST automáticas, pero no detiene por sí sola Auth ni conexiones Postgres directas; por eso los pasos anteriores las tratan por separado.

El smoke funcional/UX informado fue contra el candidato local, sin certificación independiente de cada subcaso. `docs/ENVIRONMENTS.md` define `http://localhost:3000` como runtime DEV; no existe Vercel DEV permanente ni se exige una URL hospedada. PROD no recibió R2-B. No repetir migrations, preflights ni captura anteriores, ni abrir con un runtime previo.

`202610280001_google_contact_sync_r2b_context.sql` es **PROD CONTRACT CHANGE**: revoca a clientes la RPC V1 de sync Google y concede la RPC R2-B con contexto esperado. No cambia tablas ni filas. Desde su commit, cualquier runtime que invoque la RPC V1 deja de sincronizar contactos; por eso la pausa sigue obligatoria hasta activar el cliente corregido. Si la transaction falla, queda la DB anterior y se conserva la pausa. Si falla el verifier o el smoke posterior, conservar schema/datos y gate `paused`, investigar y preparar forward-fix. El preflight registra el hash del cuerpo V1 y el estado de grants, pero no es un backup. Mantener la decisión de recuperación DEV según datos irremplazables; para PROD se exige backup recuperable y cutover independiente.
